# 正确性与可靠性根因修复复测

日期：2026-09-16。对照版本：`e4237f976462ffd34df2b42dd3ae7277641995a3`。
本记录只公开方法、合成测试与汇总结果，不包含用户原始资料、模型文件或本机路径。

## 结论

原先的主要问题不是确认门槛不够宽松，而是归属、提取完整性和状态处理存在断点。
修复后，明确单值仍直接进入“已确认”；只有真实数值冲突、无法唯一归属、版本不明
或识别不可靠的参数需要用户处理。自动确认不等于人工批准，也不会自动授权给宿主。

## 根因与修复

| 根因 | 用户看到的问题 | 修复方式 |
| --- | --- | --- |
| 纵向 SKU 与通用型号被分成不同商品 | 真冲突错过比较；明确参数变成待确认 | SKU 优先，文件/段落上下文绑定；明确多 SKU 声明逐商品适用；共用型号不靠数值相同强行认领 |
| 元数据、草稿和参数没有区分 | 备注、待核查文案混进事实 | 使用明确文档角色与标签；草稿不为自身声明提供依据；陌生的真实参数仍保留 |
| 版本主要来自文件名 | 历史差异被当作当前强冲突 | 读取明确正文版本和历史标记；同一适用版本内的不同值仍冲突 |
| 数字、编码与标签边界过窄 | 丢负号、GBK 失败、分号 CSV 漏读、SKU 前缀变字段名 | 规范符号、严格解码、分隔符识别与参数前缀分离；不猜陌生单位 |
| 一行不清楚触发整页模型重做；提示例子易诱导只返回少量行 | 扫描参数丢失，重复重试仍不全 | 保留通过原安全规则的清楚 OCR 行，只复核疑问行；按参数/口径/条数检查覆盖，缺失继续报错 |
| 复核结果固定为 0.75，门槛为 0.8 | 正确图片参数仍需逐条确认 | 单独记录复核完整性与 OCR 一致性，不修改分数冒充概率；低分相同副本不拖累清楚证据 |
| 每次只读状态查询都导出和重建报告 | 大项目刷新很慢 | 无变化只校验源哈希并读取结果；来源/决定变更及损坏状态仍走重新验证；审核卡片每批 50 条 |
| 新任务失败后顶层沿用旧成功状态 | 用户误以为新资料已参与核对 | 明示“本次更新未完成，当前显示上次结果”并提供继续处理入口 |
| 部分 Windows 文件系统不支持 fsutil 枚举 | 安装/打包被误拦截 | 用 Windows 原生文件句柄读取链接数兜底；硬链接与不安全路径仍拒绝 |
| benchmark 只核对字段名 | 错值也得到满分 | 一对一核对字段、标准值、单位；标注口径/商品时也必须相同 |

同值的无口径副本不会被当作该口径的已核验证据，也不会把其他来源的人工确认
转移给它。待定、无值和负净重等明显不合理值不能仅因“只有一个值”而自动确认。

## 固定样本复测

预期在修复前已经固定，未根据新结果修改标准答案。图片和扫描件使用实际本地
Qwen3-VL-8B INT4 OpenVINO + RapidOCR，CPU、低进程优先级、4 个逻辑核，离线加载。
模型没有收到预期答案。原始输入前后哈希一致。

| 检查对象 | 修复前 | 修复后 | 范围 |
| --- | ---: | ---: | --- |
| 边界场景 | 25/38 | 38/38 | 字段、值、单位、口径、归属及状态；少数同义规范值按预先定义的等价口径判断 |
| 主参数表目标单元格 | 55/55，另有 4 条元数据误提取 | 55/55，无额外元数据 | 同时核对商品归属 |
| 扫描铭牌可见字段 | 4/10；仅 1 项归属正确 | 10/10；10 项归属正确 | 无漏读错误，目标 SKU 正确 |
| 文案放行/拦截方向 | 7/8 | 8/8 | 使用独立正确参考事实，避免提取错误污染评分 |
| 预选工程图片 | 8/8；6 个正样本中 3 个多余待确认 | 8/8；6 个正样本无多余待确认 | 6 张含参数图片、2 张无参数/特殊图片；并非大规模泛化评估 |

9 份资料聚合后为 **62 条事实：57 已确认、4 待确认、1 冲突**。
4 条待确认分别为 3 条商品归属问题和 1 条适用版本问题。原先漏报的净重冲突已恢复，
并由回归测试保证冲突值不能进入默认导出；历史压力差异改为版本选择，不再报当前强冲突。

底层为 130 条证据候选：明确写明适用于多个 SKU 的同一来源分别绑定每个商品，
仍保留同一个来源和位置，不算多个独立来源。删除元数据与草稿事实、恢复漏读、
修正商品身份后，事实/候选数量都发生变化，不能用条数下降本身作为正确率。

## 自动化与交互验证

- 本机全量回归共 438 项，435 项通过、3 项因本机无符号链接权限跳过，207.727 秒；
  补充的事实状态/人工确认边界 38 项通过，编译检查和示例冒烟检查通过。
- 38 个固定场景位于 `tests/fixtures/accuracy_cases.json`，由 `test_accuracy_regressions.py` 执行。
- `test_reliability.py` 覆盖归属反例、跨 SKU 适用范围、缓存重跑、真冲突导出、
  草稿排除、部分视觉失败、置信分数边界、状态只读/恢复与错误值评分。
- 故障注入确认：失败后的旧结果明确标识；后续成功后清除警告。已有来源失效、
  授权、原文链接、安装与打包安全测试继续执行。
- 无界面浏览器测试验证采用、修改、撤销、本次不使用、授权、内容回检及四种屏幕宽度；
  另验证 6000 条事实只先渲染 50 条、显示更多、筛选重置和旧结果警告。

生成的 1000 商品/6000 事实压力数据：分析后首次详细状态读取 0.87 秒，后续串行
摘要/详细读取约 0.44/0.44 秒，对照版本约 13.4/15.9 秒。源文件哈希仍逐次校验，
没有把已变化来源当作有效缓存。这些数字是本机单次路径耗时，不是网络端到端延迟；
详细响应仍包含完整数据，浏览器分批渲染并不等同于后端分页。

基础回归命令：

```shell
python -m unittest discover -s tests -v
```

可选浏览器测试需本地 Playwright/Chromium（可通过 `PEG_TEST_BROWSER_CHANNEL` 指定已安装浏览器）：

```shell
node tests/check_simple_review_browser.cjs
```

## 边界

这些是固定测试包和小型定向样本的结果，不是“任意商品资料正确率 100%”。严重模糊、
复杂合并表格、未知行业简称、隐含版本关系、缺失 SKU 仍可能需要确认或补资料。
不完整识别不会被伪装成完整成功，未解决冲突不会靠多数票或自动选择最新版消除。

本轮没有控制用户桌面，没有重启或重新安装正在使用的 WorkBuddy，也不声称已验收
新的完整 WorkBuddy 云端生成任务。验证覆盖项目引擎、真实本地模型、隔离服务和
无界面审核页；安装测试使用隔离目录。
