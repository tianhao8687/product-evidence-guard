## 多并发的后果

当前实现允许多个调用同时到达，但通过全局业务锁让一个模型一次处理一个任务。
增加请求主要增加排队等待，不等同于同时推理。单张类似样本后续约 15 秒，4 个或 8 个任务的最后完成时间
可粗略按约 1 分钟或 2 分钟理解；这只是相同任务规模的推算，复杂图片、大文件夹和其他负载会改变时间。

后台最多接收 8 个处于排队/执行中的不同输出目录任务，第 9 个会被明确拒绝。
该边界用模拟执行器测试，没有让 8 份真实大模型推理同时运行。
同一输出目录重复提交会返回正在进行中的任务；不同商品必须使用不同输出目录，避免请求被合并。

确认/导出也共用业务锁，可能等待正在进行的图片分析；状态查询仍可响应。
现有任务状态有一个展示限制：排队线程可能显示 `phase=running`，而实际 `progress.stage=queued`。
测试依据实际阶段和执行时间确认串行，不能把多个 running 标签解释成多份模型同时计算。

如果绕过共享服务，分别启动多个模型实例，会额外占用内存并争用 CPU/内存带宽。
本轮单实例已用约 11.2 GiB 工作集，而系统剩余最低约 3.1 GiB，因此当前环境不宜直接多开 8B 实例。
可能出现分页、明显卡顿、推理变慢或内存分配失败；这些多实例后果是风险推断，本轮没有做多实例压力测试。
峰值工作集不能机械乘以实例数当成准确容量需求，因为共享页和每个请求的上下文会改变实际开销。

OpenVINO 对真正的吞吐优化需要应用与推理调度共同配合，并在总体吞吐和单请求延迟之间权衡，
见[官方吞吐优化说明](https://docs.openvino.ai/2026/openvino-workflow/running-inference/optimize-inference/optimizing-throughput.html)。
本轮没有改变模型调度、线程数、GPU 配置或部署模式。

## 测量边界

一张公开图片重复运行，均使用独立输出目录，业务缓存命中文件数为 0。首个业务请求明显慢于后续请求，
所以不能把 23.9 秒与并发组直接相比并宣称并发加速。该实验不等于多图片性能分布或准确率评测。
内存每 0.5 秒采样；Working Set 是驻留物理内存页，Private Bytes 是进程私有提交内存，两者不能相加。
模型测试后保持常驻，基准脚本未强制关闭任何应用或模型进程。
